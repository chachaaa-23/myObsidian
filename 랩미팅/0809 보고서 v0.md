## 2. AI가 어떤 기준으로 룰을 수정/제외했는지 파악

### 2-1. 전체 실행 흐름

```
1. docker compose up -d          # ModSecurity CRS + backend 컨테이너 기동
2. bash scripts/watchdog.sh <branch>   # 에이전트 루프 감시 프로세스 시작
      └─ watchdog.sh가 scripts/run-agent.sh를 반복 호출
            └─ run-agent.sh가 claude CLI를 매 실험(experiment)마다 새 프로세스로 호출
```

### 2-2. run-agent.sh의 역할 —매번 초기화, 새로 상태 주입

`claude` CLI는 호출될 때마다 완전히 새로운 세션으로 시작되며, 이전 실험에 대한 기억이 없다. 
대신 `run-agent.sh`가 매 호출 시 다음 정보를 프롬프트에 명시적으로 주입해 "이어서 실험하는 것처럼" 동작하게 만든다.

- 참고할 지침 파일: `program.md` (역할: 시스템 프롬프트)
- 지금까지의 진행 기록: `git log`(커밋 히스토리) + `results.tsv`(수치 기록)
- 지금까지의 최고 기록: claude 호출 시 직접 명시. 
	  `Best so far: <commit> <balanced_accuracy> ...`
- 제약: 한 번 호출에 정확히 하나의 변경만 하도록 스코프를 강제 제한

실제 호출 프롬프트(정리된 형태):

`claude --model claude-sonnet-5 --permission-mode bypassPermissions --print You are running ... remaining misses.`

```sh
"You are running experiment $EXPERIMENT in the WAF autoresearch loop.

Branch: autoresearch/$BRANCH | Commit: $CURRENT_COMMIT | Total results: $((RESULTS_COUNT - 1))
Best so far: $BEST

Read program.md for full instructions. The config files are large now.

EFFICIENT WORKFLOW (avoid timeouts):
1. Read results.tsv to see what's been tried
2. Run: python3 scripts/evaluate.py > run.log 2>&1 to see current missed/FP breakdown
3. Based on run.log, pick ONE targeted change (don't re-read full config unless needed)
4. Make the change, git add -A && git commit -m 'experiment: <description>'
5. Run evaluate again, read run.log
6. Append to results.tsv: commit<TAB>balanced_accuracy<TAB>tpr<TAB>tnr<TAB>fpr<TAB>keep|discard<TAB>description
7. If worse than best: git revert --no-edit HEAD
8. git add results.tsv && git commit -m 'results: <description>'

Do exactly ONE experiment. Focus on either removing a high-FP CRS rule or adding a targeted detection rule for remaining misses." 
```

### 2-3. program.md — 판단 기준의 원천

`program.md`는 에이전트가 매 실험에서 참고하는 지침서로, 다음 요소로 구성된다.

1. **현재 상태 파악**: `results.tsv`를 읽어 지금까지 시도된 것과 최고 기록 확인
2. **목표 및 제약 규정**
    - 최적화 목표: balanced_accuracy = (TPR + TNR) / 2 최대화
    - Simplicity criterion: 동일한 성능 개선이면 더 단순한 변경(룰 제거 > 룰 추가) 우선
    - "공격 탐지를 늘리려고 정상 트래픽을 더 막는 것"과 "오탐을 줄이려고 탐지력을 희생하는 것" 모두 금지 — 두 지표가 함께 개선되어야 인정
    - 수정 가능 파일(`config/REQUEST-900-BEFORE.conf`, `config/RESPONSE-999-AFTER.conf`)과 수정 불가 파일(`scripts/evaluate.py`, `dataset/requests.jsonl`) 명시
3. **실험 루프 순서** (10단계, 아래 2-4 참고)
4. **탐색 방향 제시 (starting directions / strategy tips)**
    - paranoia level 조정, anomaly score threshold 튜닝, 특정 CRS 룰 제거, 카테고리별 커스텀 룰 추가, content-type 허용 범위 조정 등
    - 전략: broad(전역 설정) → specific(개별 룰) 순으로 탐색, 무작정 룰을 지우기보다 threshold 조정을 먼저 시도
    - **`false_positives_by_category`와 `missed_by_category`를 근거로 다음 행동을 결정**하도록 명시

### 2-4. 실험 루프 (loop) 상세 흐름

```
1. 현재 상태 파악 (results.tsv, config/*.conf)
2. 다음 타겟 결정 (missed_by_category / false_positives_by_category)
3. 설정 파일 수정 (.conf)
4. git commit 후 evaluate.py로 재평가
5. 기존 최고 BA와 비교
   - 개선되었으면 → keep (커밋 유지)
   - 개선 없거나 악화되었으면 → git revert --no-edit HEAD
6. 결과를 results.tsv에 기록 (commit / BA / TPR / TNR / FPR / status / description)
```

### 2-5. 판단 패턴 유형화 — 실제 사례 (v4.28.0 stock 기준 재현 실험)

수집된 로그를 실제 판단 근거 기준으로 분류하면 크게 세 가지 패턴으로 나뉜다.

**패턴 A — CRS 내장 룰 제거 (threshold/policy 완화)**

> `502eaba` — CRS rule 932270 (Unix Shell Expression) 제거. 
> 	E-Commerce 트래픽에서 쿼리스트링이 shell 메타문자 패턴과 우연히 유사해 오탐 발생. FP 1253→848, TPR 손실 없음 → keep.

**패턴 B — 커스텀 룰 신규 추가 (missed_by_category 대응)**

> `f2574a4` — custom rule 1000001 (난독화된 OS 파일 경로 순회 탐지) 추가. 
> 	`missed_by_category`에서 traversal 30건이 CRS 930100/930110/930120의 디코딩 로직을 우회하는 것을 확인, 리터럴 ASCII 앵커로 직접 매칭하는 규칙 신설. traversal 미탐 30건 전량 해결, 신규 오탐 0건.

**패턴 C — 실험 후 기각 (discard, 트레이드오프 판단)**

> `2928914` — CRS rule 942100 (libinjection 기반 SQLi) 제거 시도. 
> 	E-Commerce FP의 최다 원인(42/144)이었으나, 제거 시 TPR이 0.916→0.881로 하락하며 순손실 발생 → discard.

**공통 판단 절차 (일반화)**

```
1. false_positives_by_category 1위 카테고리 확인
   → 감사 로그(audit log)를 근거로 원인 CRS rule ID를 구체적으로 특정
2. 해당 rule 제거, 또는 threshold/content-type 완화 시도
3. missed_by_category(=TPR)가 악화되면 → revert
   악화 없으면 → keep
4. missed_by_category가 특정 공격 유형에 편중되어 있으면
   → 그 유형만 좁게 잡는 정규식 기반 커스텀 룰 신설
   (넓게 잡을 경우 신규 오탐 유발 위험 → 추후 실험에서 점진적으로 좁혀감, 예: 1000004 룰의 반복 확장)
5. 동일한 BA 개선이라면 더 단순한 변경(룰 삭제 > 룰 추가) 채택
   — program.md의 simplicity criterion을 실제로 준수하는 지점
```

## 목표 3. AI 룰셋 생성 Guidance — 내부 로직과 튜닝 과정

### 3-1. 이중 가이드 구조

이 시스템은 **정적 지침(program.md)과 동적 재주입 프롬프트(run-agent.sh)** 가 결합된 이중 구조로 에이전트를 통제한다.

| 구분    | program.md                   | run-agent.sh 프롬프트           |
| ----- | ---------------------------- | --------------------------- |
| 성격    | 고정된 규칙서 (매 실험 공통)            | 매 실험마다 동적으로 생성되는 컨텍스트       |
| 담는 내용 | 목표 정의, 제약, 전체 알고리즘, 탐색 전략 힌트 | 지금 실험 번호, 현재 커밋, 지금까지 최고 기록 |
| 역할    | "이 프로젝트의 규칙은?"               | "지금 이 순간 무엇을 수정해야 하는지?"     |

에이전트가 매번 기억을 잃는 구조이기 때문에, **run-agent.sh가 매 호출마다 program.md의 요약본을 프롬프트에 재주입**하며 실질적으로 연속성을 만들어내야 함.

### 3-2. 목표와 제약 명시적 부여

- **단일 최적화 목표**: balanced_accuracy — TPR과 TNR을 동일 가중치로 취급.
	"공격만 잘 막으면 됨" 또는 "오탐만 없으면 됨"과 같은 편향된 최적화를 원천 차단

- **암묵적 페널티(simplicity criterion)**: 정량 지표에 안 잡히는 "복잡도"를 자연어 규칙으로 별도 주입  
	적합도 평가 시 "단순성"이라는 정성적 기준 추가

- **탐색 공간 제한**: 수정 가능/불가능 파일을 명시적으로 구분해, 에이전트가 평가 스크립트나 데이터셋 자체를 조작해 점수를 왜곡하는 것을 원천 차단

### 3-3. 탐색 순서에 대한 휴리스틱 부여

program.md는 에이전트가 스스로 탐색 전략을 세우게 두지 않고, 명시적인 순서를 제시한다.

- broad(전역 설정: paranoia level, threshold) → specific(개별 룰) 순서로 진행
- `missed_by_category` / `false_positives_by_category`를 "다음 행동 결정의 근거"로 삼도록 명시 -> 이 시스템의 탐색 우선순위 함수 역할을 함
- "룰을 무작정 지우지 말고 threshold 조정을 먼저 시도하라"는 지침 — 보수적 변경을 우선하도록 유도

### 요약

반복 최적화 알고리즘
